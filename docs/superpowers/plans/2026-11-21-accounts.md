# Accounts and Permissions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People sign in to the dashboard with a local account, the first administrator is created on first use, and roles grant View, Modify, Create and Delete on hosts and groups of hosts; the admin listener can serve HTTPS.

**Architecture:** `crates/core` gains `[admin] tls`, `[admin] users` and `[[server]] groups`. `crates/server` gains a users file (`access.rs`), in-memory sessions (`session.rs`) and one authorisation gate in `admin.rs` that turns every request into a `Caller` and refuses by default. The existing editing and statistics routes filter and check by the caller's grants. The Svelte page gets sign-in, first-run and a Users tab; the CLI gets `rxh user`.

**Tech Stack:** Rust (hyper, tokio, tokio-rustls, bcrypt, aws-lc-rs, toml, sha2), Svelte 5, TypeScript, Vitest, Bun.

**Spec:** `docs/superpowers/specs/2026-11-21-auth-design.md` (everything except its "OIDC" section and `[admin.oidc]` / `public_url`, which are the next plan).

## Global Constraints

- No new crate in `Cargo.toml` `[workspace.dependencies]`. A crate already there may be added to a member's dependencies.
- Rust follows `~/.claude/CLAUDE.md` (Google Rust style): no `unwrap` outside tests, no glob imports, `expect("why")`, doc comments on public items.
- Every task ends with `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` passing; UI tasks also `bun run check`, `bun run test`, `bun run build` in `crates/server/ui` with `dist/` committed.
- Tests bind to port 0 or use `rxh_test_util::free_address`; nothing outside localhost.
- Documentation moves with the code: every new key and route is in `docs/configuration.md` with an example and in `CHANGELOG.md` (unreleased) in the task that adds it; `docs/rxh.schema.json` is regenerated when the configuration model changes.
- Bearer token, and a local request without a token, stay administrator. No existing test of the admin API or the CLI may need a change in what it sends, except where a task says so.
- A request is local when the connection is local (unix socket, or TCP peer address loopback or equal to the connection's local address) **and** today's `Host`/`Origin` rule passes.
- Default deny: a route answers a caller without the `admin` role only if it was written to. A user without View on a host gets the same answer as for a host that does not exist.
- Password hashes, session ids and the setup code never appear in a response or in a log line. Passwords: 8 characters at least, 72 bytes at most.
- Cookie: `rxh_session`, `HttpOnly; SameSite=Strict; Path=/`, plus `Secure` on a TLS connection. A cookie-authenticated request other than `GET`/`HEAD` needs `Origin` equal to `Host`.
- Session lifetime 12 hours, not extended; at most 1000 sessions. Lockout: 5 failures for a name from one client address refuse that pair for 60 seconds with `429`.
- Front end rules of the web UI stay: no `innerHTML`, `{@html}`, inline script or `style=`; relative API URLs; `lib/api.ts` is the only `fetch`.
- Work on branch `auth`; commit after each task; never push.

## Review Focus

1. **A network client that forges `Host: 127.0.0.1`** on a `tls` listener without a token must not become administrator or run first-run setup without the code. Unit tests in Task 2, integration in Task 4.
2. **A route that forgot the check**: a signed-in user without `admin` calling every existing admin route (`/config`, `/metrics`, `/pools/...`, `/reload`, `/load`, `PATCH /config/...`, `/certificates`, `/upgrade`, `/stop`, `PUT /config/files/0`). One table-driven test in Task 4 that lists every route of the router and expects `403`.
3. **Escaping a grant by editing**: a user with Modify adding a group without Create on it, removing the group that gives Modify, renaming the host, or sending the TOML of the table with other `groups`. Tests in Task 6.
4. **The users file edited or broken while the daemon runs** (CLI adds a user, a hand edit leaves invalid TOML): the next request sees the new user; a broken file keeps the last good content and logs why. Test in Task 3.
5. **Locking yourself out**: removing the last `admin`, taking `admin` from yourself, deleting a role in use, a session whose user was removed. Tests in Tasks 3 and 5.

### Task 3: The users file

**Files:**
- Create: `crates/server/src/access.rs`; `crates/server/src/lib.rs` (`pub mod access;`)
- Modify: `crates/server/Cargo.toml` (`bcrypt` from dev-dependencies to dependencies, if not already a dependency)

**Interfaces:**
- Produces (all `pub`, documented; the CLI uses them):

```rust
pub enum Permission { View, Modify, Create, Delete }      // serde lowercase
pub enum Target { Group(String), Host(String) }
pub struct Grant { pub target: Target, pub allow: Vec<Permission> } // { group = "…" | host = "…", allow = […] }
pub struct Role { pub name: String, pub grant: Vec<Grant> }
pub struct User { pub name: String, pub password: String /* bcrypt */, pub roles: Vec<String> }
pub struct Access { pub user: Vec<User>, pub role: Vec<Role> }      // the file: [[user]], [[role]]

pub const ADMIN_ROLE: &str = "admin";
impl Access {
    pub fn load(path: &Path) -> Result<Self, String>;   // a missing file is an empty Access
    pub fn save(&self, path: &Path) -> Result<(), String>; // edit.rs atomic write, 0600, parents created
    pub fn validate(&self) -> Result<(), String>;
    pub fn scope(&self, roles: &[String]) -> Scope;
    pub fn add_user(&mut self, name: &str, password: &str, roles: &[String]) -> Result<(), String>;
    pub fn set_password(&mut self, name: &str, password: &str) -> Result<(), String>;
    pub fn set_roles(&mut self, name: &str, roles: &[String]) -> Result<(), String>;
    pub fn remove_user(&mut self, name: &str) -> Result<(), String>;
    pub fn put_role(&mut self, role: Role) -> Result<(), String>;      // create or replace
    pub fn remove_role(&mut self, name: &str) -> Result<(), String>;
    pub fn verify(&self, name: &str, password: &str) -> bool;          // one bcrypt compare always
}
pub enum Scope { Admin, Grants(Vec<Grant>) }
impl Scope {
    pub fn is_admin(&self) -> bool;
    pub fn permits(&self, permission: Permission, name: Option<&str>, groups: &[String]) -> bool;
    pub fn may_create(&self, groups: &[String]) -> bool;   // non-empty and Create on every one
    pub fn creatable_groups(&self) -> Vec<String>;
    pub fn names_host(&self, name: &str) -> bool;          // some grant targets this host
}
pub struct Store { /* path, cached Access, modification time */ }
impl Store {
    pub fn open(path: PathBuf) -> Self;
    pub fn read(&self) -> Access;                               // rereads when the mtime changed
    pub fn change<T>(&self, edit: impl FnOnce(&mut Access) -> Result<T, String>) -> Result<T, String>; // read, edit, validate, save
    pub fn reserved_host(&self, name: &str) -> bool;            // any role has a host grant for it
}
```

- Rules enforced by `validate` and the mutators: user and role names match `is_group_name` (user names may also contain `.` and `@`, 1 to 64 bytes); names unique; a user's roles exist or are `admin`; `admin` cannot be defined as a `[[role]]`; a grant has exactly one of `group`/`host`; `create` on a `host` grant is rejected; password 8 characters to 72 bytes; `remove_user`/`set_roles` refuse to leave no user with `admin` ("the last administrator"); `remove_role` refuses a role some user has, naming the users.
- `Store::read` on a file that no longer parses keeps the last good content and logs the error once per modification time.

```rust
pub(crate) enum Caller {
    Token,                                  // administrator
    Local,                                  // administrator
    User { name: String, scope: Scope, session: String },
    Nobody,
}
impl Caller { pub(crate) fn scope(&self) -> Scope; pub(crate) fn is_admin(&self) -> bool; pub(crate) fn label(&self) -> &str; }
fn caller(request, state, peer) -> Caller      // the order of the spec's "Who a request is"
```

- The gate in `handle`, before routing: the dashboard assets and `GET /auth/session`, `POST /auth/login`, `POST /auth/setup` are open; every other route needs `caller.is_admin()` unless the route is in an explicit list of routes that take a `Caller` (after this task: `POST /auth/logout`, `PUT /auth/password`; Task 6 adds more). `Nobody` gets `401` (with `WWW-Authenticate: Bearer` only when a token is configured), a signed-in non-admin gets `403 {"error":"this needs the admin role"}`.
- A cookie-authenticated non-`GET`/`HEAD` request without `Origin` equal to `Host` is `403`.
- Routes (JSON in and out, errors as the existing `error()`):
  - `GET /auth/session` → `{"user": null|"ana", "admin": bool, "roles": [...], "grants": [...], "creatable_groups": [...], "setup": bool, "setup_needs_code": bool, "password_login": bool, "oidc": false}`. `setup` is true while the file has no user. `password_login` is `peer.tls || peer.local`. For `Token`/`Local` callers `user` is `null` and `admin` is true.
  - `POST /auth/login {name, password}` → `204` with `Set-Cookie`; `401 {"error":"wrong name or password"}`; `429` when locked; `403` when `!password_login`.
  - `POST /auth/logout` → `204`, cookie cleared.
  - `POST /auth/setup {name, password, code?}` → creates the first user with `admin` and signs it in. Allowed only while there is no user (`409` after), to an admin caller, or with the right `code` when `peer.tls` and no token is configured; else `403`.
  - `PUT /auth/password {current, new}` → `204`; ends the user's other sessions.
- The daemon logs `no user exists yet; to create the first one from another machine use the setup code <code>` at start only when `tls` is set, no token is set and the file has no user.
- Each sign-in, failed sign-in, sign-out and setup logs one line with the name and the client address.

- Behaviour for a caller whose scope is not admin (an admin caller sees and does exactly what it does today):
  - `GET /config/files`: each file keeps `revision`, loses its text; entities: servers with View only (each gains `"permissions": ["view", …]`), upstreams reduced to `{kind, key}` (the name only), no sections. Runtime-only (provider) servers follow the same View rule through their `name` and `groups`.
  - `POST /config/entities/server`: the resulting table (form value or TOML text, after parsing) must have `groups` with `may_create`; a `name` for which `reserved_host` is true is `403 "this name is reserved"`. Other kinds `403`.
  - `PUT /config/entities/server/{key}`: Modify on the stored host; if `name` differs from the stored one `403`; Create on every group that the new table adds; Modify must still hold on the new `name`/`groups`. Other kinds `403`.
  - `DELETE /config/entities/server/{key}`: Delete on the stored host. Other kinds `403`.
  - A key that does not exist and a host without View both answer `404` with the same body. A host with View but without the needed permission answers `403`.
  - A stale revision answers `409 {"error":"the configuration changed, read it again"}` with no other field.
  - `PUT /config/files/{index}`: administrator only.
  - `GET /status` and `GET /stats/history`: only servers with View (matched by `name`, and by `groups` from the running configuration); no pool figures, no certificate or path details that the full answer has. `GET /schema`: any signed-in caller.
